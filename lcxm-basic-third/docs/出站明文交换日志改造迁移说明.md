# 出站明文交换日志改造迁移说明

本文只记录本次代码改造，供其他同结构项目复刻。功能使用方式见
《开发流程-调用他方》的“加密接口记录明文交换日志”章节。

## 改造目标

- 实际 HTTP 请求可以发送密文，但交换日志记录加密前的业务请求。
- 配置自定义响应解析器时，交换日志记录解密、解析后的业务响应。
- HTTP、请求构建、状态码、响应解密和解析异常进入自定义 `OutboundExchangeLogger`。
- 日志内容序列化或 logger 自身失败不能影响第三方请求主流程。
- 未使用明文日志能力的原有接口保持现有行为。

## 涉及文件

| 文件 | 必须迁移的改造 |
| --- | --- |
| `outbound/builder/OutboundRequestInfoBuilder.java` | 增加日志专用请求体字段及 `logRequestBody(...)`。 |
| `outbound/model/OutboundRequestInfo.java` | 保存构建器传入的日志专用请求体。 |
| `outbound/executor/HttpOutboundExecutor.java` | 使用明文请求覆盖值；记录 `responseParser` 返回的业务响应；补充日志序列化隔离和异常类型。 |
| `outbound/log/model/OutboundExchangeLog.java` | 增加 `errorType`。 |
| `outbound/log/service/Slf4jOutboundExchangeLogger.java` | 失败日志增加异常类型。 |
| `outbound/executor/HttpOutboundExecutorTest.java` | 增加明文请求、解密响应和解析异常测试。 |

`OutboundExchangeLogger` 接口和 `AbstractOutboundPartner` 不需要修改。

## 迁移步骤

### 1. 扩展请求构建器

在 `OutboundRequestInfoBuilder<T>` 增加字段：

```java
/**
 * 仅用于交换日志的明文请求体；为空时按实际 HTTP 请求体记录。
 */
private Object logRequestBody;
```

增加链式方法：

```java
/**
 * 设置交换日志使用的业务明文请求体。
 *
 * <p>当实际 HTTP body 是加密报文时，可传入加密前的请求对象。该值只参与日志序列化，
 * 不会改变实际发送内容；传入 {@code null} 表示仍按实际 HTTP 请求体记录。</p>
 *
 * @param logRequestBody 加密前的业务请求对象或明文
 * @return 当前构建器
 */
public OutboundRequestInfoBuilder<T> logRequestBody(Object logRequestBody) {
    this.logRequestBody = logRequestBody;
    return this;
}
```

如果该类使用 Lombok `@Getter`，不需要手写 getter；否则增加 `getLogRequestBody()`。

### 2. 扩展不可变请求模型

在 `OutboundRequestInfo<T>` 增加字段：

```java
/**
 * 仅用于交换日志的业务明文请求体；为空时记录实际 HTTP 请求体。
 */
private final Object logRequestBody;
```

在接收 Builder 的构造方法中复制该值：

```java
this.body = builder.getBody();
this.logRequestBody = builder.getLogRequestBody();
this.timeout = builder.getTimeout();
```

### 3. 扩展交换日志模型

在 `OutboundExchangeLog` 增加异常类型：

```java
/**
 * 异常类型全限定名；成功时为空，便于自定义日志处理器分类统计。
 */
private String errorType;
```

项目日志表需要保存异常类型时同步增加列；不需要保存时，自定义 logger 可以忽略该字段。

### 4. 调整 HTTP 执行和日志时机

在 `HttpOutboundExecutor.execute(...)` 中，先安全解析日志请求体，再构建和发送 HTTP 请求。
响应成功解析后，仅当请求配置了 `responseParser` 时，使用解析后的业务对象生成响应日志；
普通响应继续记录原始文本，避免改变存量日志格式：

```java
requestBody = safeResolveLogRequestBody(request);
HttpRequest httpRequest = buildRequest(request);
try (HttpResponse response = httpRequest.execute()) {
    httpStatus = response.getStatus();
    responseBody = response.body();
}
checkHttpStatus(httpStatus);
T result = parse(responseBody, request);
String logResponseBody = request.getResponseParser() == null
        ? responseBody : safeResolveLogResponseBody(result);
log(request, httpStatus, DateUtil.current() - start,
        requestBody, logResponseBody, null);
return result;
```

`executeBytes(...)` 也应在 `buildRequest(...)` 前调用 `safeResolveLogRequestBody(request)`，
保证请求构建和网络异常发生时，失败日志仍能拿到请求明文。

在目标项目已有的 `resolveLogRequestBody(...)` 方法首行增加以下判断，使日志专用值优先；
原有请求类型处理代码不需要改动：

```java
if (request.getLogRequestBody() != null) {
    return serializeLogValue(request.getLogRequestBody());
}
```

增加日志值序列化和隔离方法：

```java
private String safeResolveLogRequestBody(OutboundRequestInfo<?> request) {
    try {
        return resolveLogRequestBody(request);
    } catch (Exception e) {
        LOGGER.warn("resolve third outbound request log body failed", e);
        return null;
    }
}

private String safeResolveLogResponseBody(Object response) {
    try {
        return resolveLogResponseBody(response);
    } catch (Exception e) {
        LOGGER.warn("resolve third outbound response log body failed", e);
        return null;
    }
}

private String resolveLogResponseBody(Object response) throws Exception {
    return serializeLogValue(response);
}

private String serializeLogValue(Object value) throws Exception {
    if (value == null) {
        return null;
    }
    return value instanceof String
            ? (String) value : objectMapper.writeValueAsString(value);
}
```

构建 `OutboundExchangeLog` 时补充异常类型：

```java
.setStatus(resolveStatus(httpStatus, exception))
.setErrorType(exception == null ? null : exception.getClass().getName())
.setErrorMessage(exception == null ? null : exception.getMessage());
```

异常分支继续把已收到的原始 `responseBody` 交给日志。解密或解析失败时不存在可信的明文响应，
因此不能把原始报文标记为明文。

### 5. 调整默认 slf4j 失败日志

在失败日志模板中增加 `errorType={}`，并在对应位置传入 `log.getErrorType()`：

```java
LOGGER.warn(
        "[third-outbound] third={}, operation={}, method={}, url={}, httpStatus={}, status={}, "
                + "elapsed={}ms, requestBody={}, responseBody={}, errorType={}, error={}",
        log.getThirdCode(), log.getOperation(), log.getMethod(), log.getUrl(),
        log.getHttpStatus(), log.getStatus(), log.getElapsedMillis(),
        abbreviate(log.getRequestBody()), abbreviate(log.getResponseBody()),
        log.getErrorType(), abbreviate(log.getErrorMessage()));
```

### 6. 增加回归测试

至少覆盖以下场景：

- 实际 HTTP body 是密文，`OutboundExchangeLog.requestBody` 是传入的明文对象 JSON。
- `responseParser` 返回解密后的业务对象，`OutboundExchangeLog.responseBody` 是该对象 JSON。
- `responseParser` 抛出异常时业务调用失败，自定义 logger 收到 `FAILED`、异常类型和异常消息。
- 普通接口未配置 `logRequestBody`、`responseParser` 时，日志行为保持不变。

当前项目的验证命令：

```shell
mvn --% -Dtest=HttpOutboundExecutorTest -Dtest.excluded.groups= test
```

## 执行边界

响应解密位于具体 Partner 的 `responseParser(...)` 中，该回调由 `HttpOutboundExecutor.parse(...)`
在执行器的 `try/catch` 内调用，所以解密和反序列化异常会进入自定义交换日志。

请求加密通常发生在调用 `execute(...)` 之前。该阶段尚未开始 HTTP 交换，异常不会由
`HttpOutboundExecutor` 生成 `OutboundExchangeLog`。如果另一个项目需要记录这类本地前置错误，
应建立独立的业务操作日志，或者为执行器另外设计请求编码回调，不能将其误记为已经发出的 HTTP 请求。

## 兼容性检查

- 新增 Builder 方法是可选能力，存量调用不需要修改。
- `OutboundExchangeLogger` 方法签名不变，已有实现可以继续使用。
- 只有配置 `responseParser` 的成功请求改为记录解析后的响应对象。
- 自定义日志落库若采用固定字段，可按需要增加 `errorType` 列。
- 明文可能包含敏感字段，迁移后应复核脱敏、日志权限和保存周期。
